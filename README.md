# خلف الإجابة

لعبة متصفح تفاعلية تأخذ المستخدم من استخراج المواد وتصنيع المكونات إلى مراكز البيانات ومواد البيانات والعمل البشري والتدريب الإضافي والتقييم وتشغيل الخدمة، بهدف كشف العمل والبنية المادية اللذين تختصرهما واجهة الذكاء الاصطناعي.

## مبدأ التصميم التعليمي

لا تفترض اللعبة معرفة مسبقة بسلسلة الذكاء الاصطناعي. تعرض مقدمة كل مرحلة العنوان، ولماذا ترتبط بالرحلة، والمهمة المطلوبة؛ بينما ينتقل المكان والعاملون والمصطلحات والتفاصيل التقنية إلى قسم اختياري.

الحلقة الأساسية هي: `شخص → مهمة → قيد أو حدث → قرار → أثر مرئي → ناتج تقني مختصر`. لا تُستخدم نقرات الكشف كشرط للتقدم عندما لا تحمل قرارًا: استكشاف مصادر البيانات اختياري، وأدوار مركز البيانات تظهر مباشرة. بعد كل مرحلة رئيسية يرى اللاعب كيف يتحول العمل الذي رآه إلى اسم أو ناتج تقني مختصر.

تظهر آثار القرارات في موضعها أو في مرحلة لاحقة عندما توجد علاقة سببية واضحة. خلل السلامة مثلًا يمر عبر إصلاح وإعادة اختبار قبل بوابة الإطلاق، بينما طريقة استعادة الخدمة تؤثر في حالة وصول الطلب النهائي من دون تغيير صياغة الإجابة نفسها.

لا توجد منظومة نقاط أو مقاييس كمية خفية وراء النتيجة النهائية. تعرض شاشة النهاية القرارات نفسها وآثارها ضمن محاور مستقلة، وتفصل بين أداء المقيّم والسلامة والجاهزية والتشغيل.

## التشغيل

المشروع يعمل بالكامل داخل المتصفح: لا خادم خلفي، ولا قاعدة بيانات، ولا خطوة بناء، ولا تبعيات تشغيل خارجية.

أثناء التطوير شغّل خادم ملفات محليًا:

```bash
python3 -m http.server 8000
```

ثم افتح `http://localhost:8000`.

## بنية المشروع

```text
index.html
assets/images/{characters,scenes}/
css/
js/
  app.js
  core/
    state.js
    storage.js
    decisions.js
    router.js
    ledger.js
    audio.js
    accessibility.js
  data/
  components/
  scenes/
tests/
docs/
.github/workflows/
```

- `js/core/state.js`: الحالة الحالية فقط؛ لا يخزن قيمًا مشتقة أو مقاييس خفية.
- `js/core/decisions.js`: سجل القرارات السببية التي يمكن عرضها للمستخدم لاحقًا.
- `js/data/chapters.js`: تعريف المراحل التسع وعلاقتها بالسلسلة.
- `js/data/content-tasks.js`: حالات البيانات والتصنيف والتقييم والدعم.
- `js/data/stage-tasks.js`: المهمة الأساسية لكل مرحلة وشروطها وقيودها.
- `js/components/`: التقدم، المهمة، الشخصيات، الاختزال والحوارات.
- `js/scenes/`: منطق التفاعلات الخاصة بكل مرحلة.

## الخصوصية

لا ترسل اللعبة بيانات إلى أي خادم. التقدم والإعدادات تحفظ فقط في `localStorage` ويمكن حذفها من إعدادات اللعبة. تقبل الحالة المحفوظة مخطط النسخة الحالية كاملًا فقط؛ لا توجد migration أو طبقة توافق مع بنى قديمة.

## الدقة التقنية

- التعدين يربط تحذير القطاع ب بالعمل فيه فعلًا.
- تصنيع المكونات يستخدم مؤشرات تعليمية معلنة؛ فرق الضغط معروض بالـPa لا كضغط مطلق مضلل.
- إجراء تركيب الخادم خاص بالسيناريو، ولا يفرض ترتيبًا عالميًا زائفًا بين الطاقة والشبكة.
- مواد البيانات قد تستخدم في التدريب أو الضبط أو التقييم؛ التنقيح لا يحسم تلقائيًا الحقوق أو كل مخاطر إعادة التعرف.
- مرحلة التدريب تمثل جولة `post-training` مبسطة تبدأ من checkpoint، وليست تدريب نموذج كامل من الصفر.
- لا تستخدم اللعبة نسب حمل غير مشتقة من المعطيات؛ تعرض السعة المتبقية وهامش الأعطال فقط.
- أداء اللاعب كمقيّم لا يغير خصائص النموذج تلقائيًا.
- خلل السلامة يوقف المرور المباشر إلى الإطلاق حتى يمر بإصلاح وإعادة اختبار.
- توزيع الحمل له عدة حلول صحيحة ضمن سعات 60/45/35، ويشجع على الاحتفاظ بهامش تشغيل.
- المراحل التاريخية لا تعاد عند كل طلب؛ الاستخدام اللحظي يعتمد على بنية ونموذج بُنيا مسبقًا.

## التحقق الآلي

Workflow `Validate static game` يتحقق من سلامة JavaScript وESLint والبنية والمراجع ومخطط التخزين وCSS، ثم يشغّل رحلة كاملة عبر Playwright على سطح المكتب والهاتف. كما يغطي اختبارات سببية مستقلة، منها:

- تحذير التعدين لا يظهر من قطاع آخر.
- الطاقة والشبكة متاحتان بصورة مستقلة بعد تثبيت الخادم.
- استكشاف مصادر البيانات اختياري، وقرار حالة البيانات الشخصية/الحقوق يُسجل.
- الاستراحة غير المدفوعة تزيد الزمن الظاهر والعائد المحسوب مقابل الوقت.
- التدريب لا يعرض نسب 97%/84% الزائفة.
- المثال القانوني يقبل «كلتاهما سيئة» عندما تحذف إحداهما قيدًا وتضيف الأخرى معلومة.
- السلامة بوابة فعلية قبل الإطلاق.
- أكثر من توزيع حمل يمكن أن ينجح إذا احترم السعات.
- الحالة الحالية لا تحتوي `metrics` أو حالة كشف عمال مشتقة.

اللعبة نفسها لا تحتاج أي مكتبة خارجية وقت التشغيل؛ Playwright يثبت داخل CI للاختبار فقط.
