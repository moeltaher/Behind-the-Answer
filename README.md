# خلف الإجابة

لعبة متصفح تفاعلية تأخذ المستخدم في رحلة من استخراج المواد وتصنيع المكونات وتجميع الأجهزة إلى مراكز البيانات والبيانات وتدريب النموذج والتقييم البشري وتشغيل الخدمة، بهدف كشف العمل البشري والبنية المادية خلف أنظمة الذكاء الاصطناعي.

## مبدأ التصميم التعليمي

لا تفترض اللعبة أن المستخدم يعرف سلسلة إمداد الذكاء الاصطناعي أو مصطلحاتها. تبدأ كل مرحلة بمقدمة قصيرة تجمع المكان وعلاقته بالإجابة ومن يعمل فيه والمهمة المطلوبة، بينما تبقى التفاصيل الموسعة اختيارية.

الحلقة الأساسية هي: مهمة → قيد أو حدث → قرار → أثر مرئي → ناتج ينتقل إلى المرحلة التالية. بعض القرارات يمتد أثرها إلى مراحل لاحقة عندما توجد علاقة سببية واضحة؛ مثل تأثير السعة ونقطة الحفظ في نطاق التحقق قبل الإطلاق، أو تأثير طريقة استعادة الخدمة في حالة وصول الطلب النهائي.

لا تجمع شاشة النهاية أعمالًا مختلفة في درجة واحدة. تعرض النتائج القرارات نفسها وآثارها داخل محاور مستقلة، وتفصل بين أداء المقيّم، واختبار السلامة، وجاهزية الإطلاق، وتشغيل الخدمة.

## التشغيل

المشروع يعمل بالكامل داخل المتصفح: لا خادم خلفي، ولا قاعدة بيانات، ولا خطوة بناء، ولا تبعيات تشغيل خارجية.

ولأن الكود مقسم إلى وحدات JavaScript، استخدم خادم ملفات محليًا أثناء التطوير:

```bash
python3 -m http.server 8000
```

ثم افتح:

```text
http://localhost:8000
```

- `js/data/stage-backgrounds.js`: المصدر المركزي لربط المشاهد بالمراحل والخلفيات.

- `js/scenes/`: التفاعلات الخاصة بكل مرحلة رئيسية.
- `tests/`: فحوص البنية وCSS ومخطط التخزين والرحلة الكاملة والسببية بين المراحل.

لشرح تفصيلي لمسؤولية كل جزء وقواعد إضافة مشاهد جديدة، راجع `docs/CODE-STRUCTURE.md`.

## الخصوصية

لا ترسل اللعبة بيانات إلى أي خادم. التقدم والإعدادات تحفظ فقط في `localStorage` داخل المتصفح ويمكن حذفها من إعدادات اللعبة.

الحالة المحفوظة تقبل بنية النسخة الحالية فقط. إذا لم تطابق البيانات المخزنة هذا الشكل كاملًا، تبدأ اللعبة من الحالة الافتراضية بدل تحويل البيانات أو دمجها أو ترقيعها. لا توجد طبقة migration أو توافق مع مخططات أقدم.

## الدقة التقنية

تفرق اللعبة بين بناء النظام سابقًا وبين ما يحدث عند استخدامه. التعدين والتصنيع وتجهيز البيانات والتدريب لا تتكرر مع كل طلب. عند إرسال المستخدم طلبه، تعتمد الإجابة على بنية ونموذج بُنيا مسبقًا وعلى الخوادم والخدمات التي تعمل في اللحظة الحالية.

السيناريو لا يدعي تمثيل سلسلة توريد واحدة لكل نموذج. الشخصيات والأرقام وحدود المؤشرات افتراضية ومركبة، وتستخدم لتوضيح علاقات العمل والوقت والسعة والمخاطرة. كذلك لا تجعل اللعبة دقة اللاعب في مهمة تقييم بشرية تغير «جودة النموذج» تلقائيًا؛ فهي تسجل أداء عملية التقييم منفصلًا.

## التحقق الآلي

يوجد GitHub Actions workflow باسم `Validate static game` يعمل مع Pull Requests وعلى فرع `main`. يتحقق من:

- سلامة صياغة جميع ملفات JavaScript وملفات الاختبار.
- عدم وجود imports أو متغيرات أو دوال JavaScript محلية غير مستخدمة.
- سلامة الاستيرادات المحلية ومراجع CSS/JavaScript من `index.html`.
- عدم وجود ملفات JavaScript تشغيلية أو exports تشغيلية أو ملفات CSS أو أصول صور غير مستخدمة.
- عدم وجود CSS class selectors أو custom properties أو `@keyframes` غير مستخدمة، بما في ذلك متغيرات CSS المشار إليها من JavaScript.
- قبول `localStorage` لمخطط الحالة والإعدادات الحالي فقط ورفض الحقول الزائدة أو أشكال الحالة السابقة.
- تطابق جميع المشاهد المسجلة مع خريطة المراحل ووجود مرجع دخول لكل مشهد.
- مرور الرحلة كاملة عبر Playwright على سطح المكتب والهاتف.
- أن قرار الاستمرار في التعدين لا يكمل الحصة تلقائيًا، وأن التوقف لا ينتج مواد.
- أن قرار التبريد يمر بنتيجة إصلاح أو نقل قبل إعلان البنية جاهزة.
- أن سعة التدريب ونقطة الحفظ تغيران أثر العطل ونطاق التحقق اللاحق.
- أن أداء المقيّم لا يغير مقاييس النظام أو جودة النموذج تلقائيًا.
- أن توزيع الحمل يحترم سعات المراكز بدل افتراض تساويها.
- أن طريقة استعادة الخدمة يمكن أن تغير حالة وصول الطلب من دون تغيير نص الإجابة نفسه.
- أن لوحة المهمة غير لاصقة على الهاتف، وأن تفاصيلها الكاملة تتحول إلى عمود واحد في الشاشات الضيقة.
- أن الهوية البصرية تتغير بحسب المرحلة الحالية.

اللعبة نفسها لا تحتاج أي مكتبة خارجية وقت التشغيل؛ Playwright يثبت داخل CI لأغراض الاختبار فقط.
