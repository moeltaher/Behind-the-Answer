# خلف الإجابة

لعبة متصفح تفاعلية تأخذ المستخدم عبر ثماني مراحل لعب: استخراج المواد، تصنيع المكونات، مراكز البيانات، تجهيز مواد البيانات، عمل التصنيف البشري، post-training، التقييم والجاهزية، ثم تشغيل الخدمة. بعد ذلك تأتي خاتمة مستقلة تعيد المستخدم إلى الطلب والإجابة وتختبر نقل الفكرة إلى منتج تقني مختلف.

## مبدأ التصميم التعليمي

لا تفترض اللعبة معرفة مسبقة بسلسلة الذكاء الاصطناعي. الحلقة الأساسية هي:

`شخص → مهمة → قيد أو حدث → قرار → أثر مرئي → ناتج تقني مختصر`

تفرق اللعبة صراحة بين **ترتيب اللعب** و**بنية النظام**. شريط المراحل خطي للتعلم، بينما الخاتمة تعيد رسم النظام إلى مسار مادي طويل الأجل، ودورة تطوير متكررة، وتشغيل مستمر. لا توجد درجة كلية خفية تجمع العمل والحقوق والجودة والموثوقية في رقم واحد.

## التشغيل

المشروع يعمل بالكامل داخل المتصفح: لا خادم خلفي، ولا قاعدة بيانات، ولا خطوة بناء، ولا تبعيات تشغيل خارجية.

أثناء التطوير:

```bash
python3 -m http.server 8000
```

ثم افتح `http://localhost:8000`.

توجد تبعيات تطوير واختبار فقط في `package.json`.

منطق كل مرحلة يوجد داخل ملفها في `js/scenes/`. لا توجد طبقة post-render تعيد كتابة المشهد بعد رسمه؛ حُذف `audit-enhancements.js` حتى يبقى لكل ميكانيكية مصدر حقيقة واحد.

## الخصوصية والحفظ

لا ترسل اللعبة بيانات إلى أي خادم. التقدم والإعدادات تحفظ فقط في `localStorage` ويمكن حذفها من إعدادات اللعبة.

الحالة الحالية تستخدم `schemaVersion: 3`. طبقة التخزين تتحقق من القيم والعلاقات السببية بين الحقول، وليس من الأنواع فقط. يوجد migration صريح من v2: إذا كان الحفظ القديم قد وصل إلى التدريب أو ما بعده، يحتفظ بالتقدم السابق الممكن إثباته ويعيد اللاعب إلى `trainingSetup` لأن v2 لم يكن يحفظ أهلية البيانات أو تقييم checkpoint أو أدلة الإصدار أو اختبارات failover الجديدة. إذا تعذر ترحيل الحفظ بأمان، تبدأ جلسة جديدة مع إشعار واضح.

## الدقة التقنية والمنطقية

- التعدين يجعل تأجيل فحص القطاع الأسرع مفاضلة فعلية؛ استمرار الاستخدام بعد التحذير يمكن أن يحول الصيانة المؤجلة إلى فحص إلزامي، من دون اختراع إصابة عشوائية.
- المصنع يفصل جودة الوحدات التي اجتازت الفحص عن **دين الصيانة**. استمرار الإنتاج قد يترك تحقيق سبب ارتفاع الجسيمات مفتوحًا، ولا يمحوه اجتياز المنتج للفحص.
- في مركز البيانات، نقل workload إلى سعة بديلة يحافظ على الاستمرارية لكنه لا يصلح المجموعة الأصلية. لا تصبح القدرة جاهزة قبل إصلاح التبريد وإعادة الاختبار.
- مرحلة البيانات تفصل بين **مرور المادة في workflow** وبين **حسم الحقوق والخصوصية والملاءمة**.
- قبل post-training توجد بوابة أهلية مستقلة: المادة `ready` ذات المسألة غير المحسومة يجب إما إيقافها قبل المعالجة أو إدخالها بقرار صريح. تحفظ `dataTrainingHeld` ما لم يدخل الجولة، وتحفظ `dataTrainingUsed` ما عولج فعلًا.
- `dataTrainingUsed` تاريخ سببي لا يُمحى إذا استُبعدت المادة لاحقًا. إذا كانت المادة قد دخلت التطوير بالفعل وتعذر حسم حاجبها، تعرض اللعبة التخلص من النسخة الناتجة وإعادة الجولة من دونها بدل الادعاء أن الاستبعاد اللاحق يمحو الاستخدام السابق.
- عامل التصنيف يرى دليل المشروع قبل العمل، ثم يحصل في المراجعة على تفسير مثالًا بمثال يفرق بين اختيار العامل وقرار المراجع.
- التدريب يمثل post-training مبسطًا بحد سعة افتراضي معلن، لا وصفًا عامًا لتحمل الأعطال.
- تقييم checkpoint أصبح مقارنة فعلية لثلاثة أمثلة مرتبطة بهدف التغيير؛ لا تفترض اللعبة أن النسخة الأحدث أفضل لمجرد حداثتها.
- إصلاح خلل السلامة وإعادة اختباره إلزاميان قبل الجاهزية.
- بوابات الإصدار الأساسية مبنية على أدلة. بوابة السعة تعرض أولًا نتيجة 92% مقابل حد تنبيه 90%، فلا يمكن اعتمادها حتى التحقيق وإعادة القياس إلى نتيجة مقبولة في السيناريو.
- اسم بوابة المخاطر هو **السلامة والخصوصية وحوكمة البيانات**؛ لا تدعي اللعبة اختبار cybersecurity لم تتم محاكاته.
- الأعمال الإضافية الناتجة عن checkpoint حديث أو الاستمرار عند حد السعة منفصلة عن الحواجز الأساسية ويمكن نقلها إلى المراقبة فقط عندما تكون غير حاجبة.
- توزيع الحمل يقبل عدة حلول صحيحة. بعد اعتماده يختبر اللاعب حالات N-1 الثلاث: خروج أ أو ب أو ج، ويقارن الحمل المزاح بالهامش في الموقعين الآخرين. أزيل «إجمالي headroom» لأنه ثابت رياضيًا لأي توزيع صالح في هذا السيناريو.
- العطل التشغيلي اللاحق لا يُنسب تلقائيًا إلى توزيع الحمل؛ التشخيص هو الذي يحدد المشتبه الرئيسي.
- الخاتمة لا تخترع عدد محاولات أو زمن استجابة غير ممثل في اللعب، وتوضح أن بعض المنتجات قد تضيف routing أو retrieval أو moderation أو tool calls أو caching أو logging وقت الطلب بحسب التصميم.
- تحدي نقل التعلم يستخدم خدمة RAG ويطلب تصنيف عناصر إلى: بُني قبل الطلب، يحدث مع الطلب الحالي، أو تشغيل مستمر.
- سجل النتائج الكامل يستخدم تصنيفًا مركزيًا مع fallback، واختبار آلي يضمن أن عدد القرارات المعروضة يساوي عدد `state.decisions`.

## الوصول

- RTL أساسي.
- الانتقال بين المشاهد ينقل التركيز إلى عنوان المشهد الجديد.
- لا يستخدم المشهد كله `aria-live`; رسائل feedback المحددة تستخدم `role="status"` عند الحاجة.
- المرحلة الحالية تحمل `aria-current="step"`.
- عند عدم وجود اختيار محفوظ، يبدأ تقليل الحركة من `prefers-reduced-motion` في نظام التشغيل.
- الحوارات تحمل أسماء واضحة لقارئات الشاشة، ومناطق التمرير الأفقية قابلة للوصول بلوحة المفاتيح.

- سلامة البنية والمراجع والـroutes والأصول
- مخطط التخزين v3 والعلاقات السببية وmigration
- سلامة CSS
- رحلة Chromium كاملة على desktop وmobile
- اختبارات الحوكمة والسببية وإعادة التحميل
- migration من v2 داخل متصفح حقيقي
- مصفوفة axe للمشاهد الديناميكية
- Firefox وWebKit smoke
- `tests/third-audit.mjs` كـ regression مخصص لمشكلات جولة المراجعة الثالثة
