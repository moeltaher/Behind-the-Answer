# خلف الإجابة

لعبة متصفح تفاعلية تأخذ المستخدم عبر ثماني مراحل لعب: استخراج المواد، تصنيع المكونات، مراكز البيانات، تجهيز مواد البيانات، عمل التصنيف البشري، post-training، التقييم والجاهزية، ثم تشغيل الخدمة. بعد ذلك تأتي خاتمة مستقلة تعيد المستخدم إلى الطلب والإجابة وتختبر نقل الفكرة إلى منتج تقني مختلف.

## مبدأ التصميم التعليمي

لا تفترض اللعبة معرفة مسبقة بسلسلة الذكاء الاصطناعي. الحلقة الأساسية هي:

`شخص → مهمة → قيد أو حدث → قرار → أثر مرئي → ناتج تقني مختصر`

تفرق اللعبة صراحة بين **ترتيب اللعب** و**بنية النظام**. شريط المراحل خطي للتعلم، بينما الخاتمة تعيد رسم النظام إلى مسار مادي طويل الأجل، ودورة تطوير متكررة، وتشغيل مستمر. لا توجد درجة كلية خفية تجمع العمل والحقوق والجودة والموثوقية في رقم واحد.

كل مشهد في اللعبة يعرض العنصر نفسه **«مهمتك الآن»**. لا توجد قائمة مشاهد مستثناة. وفي المشاهد التفاعلية تصف اللوحة الإجراء الحالي نفسه، مثل حسم متابعة خصوصية مادة أو إعادة اختبار السلامة أو قبول فجوة مرونة، بدل الاكتفاء بعنوان المرحلة العامة. شاشات النتائج والانتقال المناسبة تعرض حالة المهمة مكتملة بوضوح.

## التشغيل

المشروع يعمل بالكامل داخل المتصفح: لا خادم خلفي، ولا قاعدة بيانات، ولا خطوة بناء، ولا تبعيات تشغيل خارجية.

أثناء التطوير:

```bash
python3 -m http.server 8000
```

ثم افتح `http://localhost:8000`.

توجد تبعيات تطوير واختبار فقط في `package.json`.

## الخصوصية والحفظ

لا ترسل اللعبة بيانات إلى أي خادم. التقدم والإعدادات تحفظ فقط في `localStorage` ويمكن حذفها من إعدادات اللعبة.

الحالة الحالية تستخدم `schemaVersion: 4`. طبقة التخزين تتحقق من القيم والعلاقات السببية **ومن اتساق المشهد الحالي مع التقدم**. يوجد migration من v3 وv2 والإصدارات الأقدم. إذا وصل الحفظ القديم إلى post-training أو ما بعده، يعاد اللاعب إلى `trainingSetup` مع الاحتفاظ بالتقدم السابق الممكن إثباته؛ لأن الإصدارات السابقة لا تملك معلومات تكفي لإثبات أن بيانات وأدلة التقييم والسلامة والإصدار تخص النسخة المرشحة الحالية.

## الدقة التقنية والمنطقية

- التعدين يجعل تأجيل فحص القطاع الأسرع مفاضلة فعلية، ولا يخترع إصابة عشوائية لصناعة العقوبة.
- المصنع يفصل جودة الوحدات عن **دين الصيانة**؛ إذا أكمل اللاعب الدفعة بعد التنبيه، يمكنه لاحقًا تنفيذ نافذة صيانة مستقلة وإغلاق السبب أو ترحيل الدين صراحة إلى الوردية التالية. اجتياز المنتج للفحص لا يمحو السبب المفتوح.
- في مركز البيانات، نقل workload يحافظ على الاستمرارية لكنه لا يصلح المجموعة الأصلية. لا تصبح القدرة جاهزة قبل إصلاح التبريد وإعادة الاختبار.
- مرحلة البيانات تفصل بين مرور المادة في workflow وبين حسم الحقوق والخصوصية والملاءمة.
- قبل post-training تسجل `dataTrainingApproved` السماح الصريح لمادة غير محسومة، و`dataTrainingHeld` ما أوقف قبل المعالجة.
- `dataCurrentTrainingUsed` يمثل المواد الموجودة في revision الحالية، بينما `dataTrainingUsed` سجل تاريخي لا يُمحى إذا خرجت المادة من نسخة لاحقة.
- كل جولة post-training تنشئ `candidateRevision`. إذا استبعدت مادة مستخدمة بما يستلزم إعادة الجولة، تنشأ revision جديدة وتُبطل **صلاحية** أدلة التقييم والسلامة وبوابات الإصدار للنسخة السابقة، لكن القرارات والعمل الذي حدث فعلًا في النسخة السابقة يبقيان في `decisions` و`ledger` كسجل تاريخي.
- يسمح `ledger` بأكثر من سجل للفصل نفسه عندما تتكرر دورة التطوير. يعرض دفتر السلسلة السجل الأحدث أولًا ويحتفظ بسجلات revisions السابقة تحت تاريخ قابل للفتح بدل أن يعرض نسخة قديمة باعتبارها الحالية.
- لا يمكن بدء post-training بلا أي مدخل بيانات مؤهل ولا مثال تصنيف بشري مؤكد.
- عامل التصنيف يرى دليل المشروع قبل العمل، ثم يحصل على تفسير مثالًا بمثال يفرق بين اختيار العامل وقرار المراجع.
- بعد مهام تقييم النموذج توجد خطوة **معايرة للمقيّم** قبل استخدام تقييمه كدليل. إذا أخطأ المقيّم في المهام الأصلية، يجب أن ينجح في عينة تحقق جديدة؛ لا تكفي قراءة التعليمات والضغط على زر.
- تقييم checkpoint مقارنة فعلية لثلاثة أمثلة، ولا تفترض اللعبة أن النسخة الأحدث أفضل لمجرد حداثتها.
- إصلاح خلل السلامة وإعادة اختباره إلزاميان قبل الجاهزية.
- بوابة **السلامة والخصوصية وحوكمة البيانات** لا يمكن اعتمادها إذا كانت revision الحالية تحتوي مادة ذات مسألة حوكمة غير محسومة.
- بوابة السعة تعرض أولًا نتيجة 92% مقابل حد تنبيه 90%، فلا يمكن اعتمادها حتى التحقيق وإعادة القياس إلى 84% في السيناريو.
- الأعمال الإضافية في بوابة الإصدار تشرح **سبب ظهورها**: اختيار checkpoint الأحدث يولد تحقق checkpoint الموسع، والاستمرار بثماني مجموعات بعد العطل يولد فحص استقرار. ما ينقل صراحة إلى المراقبة يحفظ في `deferredExtraChecks` ويجب تنفيذه بعد الإطلاق قبل متابعة التشغيل.
- توزيع الحمل يقبل عدة حلول صحيحة. اختبار N-1 يضيف إلى حدود السعة **حد استقبال طوارئ معلنًا قدره 20 نقطة لكل مركز باقٍ**. ومع حمل إجمالي 100% والسعات 60/45/35، لا يمكن تحقيق 3/3 لكل حالات خروج مركز واحد؛ لذلك تعرض اللعبة القيد البنيوي صراحة وتطلب إعادة التوزيع لتحسين الوضع أو قبول فجوة المرونة وتسجيلها قبل المتابعة، بدل عرض نتيجة ضعيفة كأنها نجاح.
- العطل التشغيلي اللاحق لا يُنسب تلقائيًا إلى توزيع الحمل أو إلى الفحوص المؤجلة؛ التشخيص هو الذي يحدد المشتبه الرئيسي.
- الخاتمة تعرض lineage البيانات: ما هو في النسخة الحالية، وما استُخدم تاريخيًا فقط، وما أوقف قبل التدريب، وما بقي معلقًا.
- تحدي RAG لا يكتفي بعدد الأخطاء؛ يشرح لكل عنصر خاطئ لماذا ينتمي إلى زمن مختلف.
- سجل النتائج الكامل يستخدم تصنيفًا مركزيًا مع fallback، ويجب أن يعرض كل `state.decisions`. أما بطاقات الملخص فتختار **أحدث** قرار مطابق للأولوية، حتى لا تبرز retraining قديمة بعد وجود revision أحدث.

## الوصول

- RTL أساسي.
- الانتقال بين المشاهد ينقل التركيز إلى عنوان المشهد الجديد.
- إعادة رسم المشهد نفسه بعد إجراء لا تترك التركيز على عنصر حُذف؛ ينتقل إلى feedback ظاهر أو إلى عنوان المشهد.
- لا يستخدم المشهد كله `aria-live`; رسائل feedback المحددة تستخدم `role="status"` عند الحاجة.
- المرحلة الحالية تحمل `aria-current="step"`.
- عند عدم وجود اختيار محفوظ، يبدأ تقليل الحركة من `prefers-reduced-motion` في نظام التشغيل.
- الحوارات تحمل أسماء واضحة لقارئات الشاشة، ومناطق التمرير الأفقية قابلة للوصول بلوحة المفاتيح.
- على الشاشات الصغيرة تبدأ المشاهد من أعلى بدل إعادة تمركز المحتوى رأسيًا؛ هذا يحافظ على ثبات لوحة «مهمتك الآن» وأزرار المتابعة عندما يتغير طول المشهد.

## التحقق الآلي

Workflow `Validate static game` يشغل:

- `npm audit --audit-level=high`
- فحص JavaScript syntax وESLint
- سلامة البنية والمراجع والـroutes والأصول
- مخطط التخزين v4 والعلاقات السببية وmigration
- سلامة CSS
- رحلة Chromium كاملة على desktop وmobile
- اختبارات الحوكمة والسببية والمراقبة وإدارة التركيز
- migration من v3 داخل متصفح حقيقي
- مصفوفة axe للمشاهد الديناميكية
- Firefox وWebKit smoke
- `tests/third-audit.mjs` بعد تحديثه إلى semantics v4
- `tests/fourth-audit.mjs`
- `tests/fifth-audit.mjs` لحفظ تاريخ revisions، المعايرة الفعلية، عداد أهلية البيانات، وظهور «مهمتك الآن» بصورة عامة
- `tests/sixth-audit.mjs` للـledger متعدد revisions، إغلاق/ترحيل دين الصيانة، المهام contextual، أسباب الفحوص الإضافية، فجوة N-1، وأحدث قرار في الملخص
