# خلف الإجابة

لعبة متصفح تعليمية تكشف العمل البشري والبنية المادية والتنظيمية التي تختصرها واجهة الذكاء الاصطناعي في إجابة تبدو فورية.

يمر اللاعب عبر ثماني مراحل: المواد، تصنيع المكونات، مراكز البيانات، تجهيز مواد البيانات، التصنيف البشري، التدريب الإضافي، التقييم والجاهزية، ثم تشغيل الخدمة. بعد ذلك تعيد الخاتمة رسم ما حدث إلى ثلاثة مسارات متداخلة: بناء مادي طويل الأجل، دورة تطوير متكررة، وتشغيل مستمر.

## مبدأ التصميم

الحلقة الأساسية هي:

`شخص → مهمة → قيد/حدث → قرار → عمل أو دليل → أثر مرئي → اختصار تقني`

ترتيب المراحل ترتيب تعليمي، وليس وصفًا هندسيًا يقول إن التعدين والتصنيع والتدريب تتكرر عند كل طلب.

القاعدة المنهجية الأهم: **القرار لا يساوي تنفيذ العمل الذي ينشأ عنه.** لذلك:

- إيقاف خط المصنع لا يشخّص سبب تنبيه الجسيمات ولا يصلحه؛ الإغلاق يمر بالتشخيص ثم الإصلاح وإعادة القياس، وبعدها يُستأنف الإنتاج ويُنفذ الفحص النهائي كعملين مستقلين.
- قرار الاستمرار في المصنع لا يكمل الدفعة ولا يجعلها تجتاز الفحص؛ إكمال الإنتاج والفحص النهائي فعلان صريحان لاحقان.
- إيقاف اختبار مركز البيانات لا يصلح التبريد تلقائيًا؛ يجب تنفيذ الإصلاح والتحقق وإعادة الاختبار.
- التوقف في جولة التدريب لا يعيد مجموعة الحوسبة تلقائيًا؛ الاستعادة والتحقق خطوتان منفصلتان.
- تشخيص ارتفاع الذاكرة لا يخفض القياس قبل تعديل الإعداد وإعادة القياس.
- إعادة التشغيل أو الرجوع إلى الإصدار السابق لا يثبتان عودة الخدمة قبل التحقق الصحي، وإعادة التشغيل لا تغلق السبب المشتبه به تلقائيًا.
- مراجعة ترخيص لا تحسم الحقوق قبل ظهور الدليل واعتماده.
- اعتماد الإصدار لا يفتح الخدمة؛ فتح حركة المستخدمين فعل تشغيل مستقل بعد اختبار التوزيع والمرونة.

## ما تغير في البنية الحالية

- **حالة التشغيل صريحة، وسجل القرارات تاريخ فقط.** الحقول داخل `flags`/enums تحدد الوضع الحالي؛ `decisions` يسجل ما حدث ولا يستخدم كحالة خفية للتحكم في المشهد.
- **فحص التعدين state machine صريح.** `idle / inspect / diagnosed / repaired / verified` يسمح بالاستئناف الصحيح بعد إعادة التحميل من دون استنتاج حالة التشغيل من سجل القرارات.
- **الإنتاج والفحص في المصنع منفصلان.** حالة الدفعة تمر من انتظار الإكمال إلى اكتمال الإنتاج ثم اجتياز الفحص، بينما تبقى الصيانة مسارًا مستقلًا.
- **حالة مسار البيانات مستقلة عن الأدلة.** `ready / pending / excluded` لا تعيد كتابة ما كان معروفًا عن الحقوق والخصوصية والملاءمة، والإجراءات المعروضة تختلف بحسب نوع المادة بدل تكرار قائمة موحدة غير منطقية.
- **الحوسبة ليست حالة تاريخية قابلة للاختيار.** المشروع يخصص 8 مجموعات في السيناريو من قاعدة المجال، والقرار الحقيقي عند العطل هو التوقف للإصلاح أو الاستمرار عند الحد الأدنى مع دين تحقق للاستقرار.
- **معالجة حواجز البيانات حسب المشكلة.** ترخيص الكود يُراجع بالدليل، وبيانات الاتصال يمكن تنقيحها مع إعادة التدريب، بينما الاستبعاد يستخدم عندما لا يمثل السيناريو معالجة كافية.
- **الجاهزية مقسمة إلى مهام واضحة.** مراجعة الحوكمة منفصلة عن بوابات الإصدار وعن قرار الفحوص الإضافية والإصدار.
- **قرار الإصدار لا يعني فتح الخدمة.** بعد اعتماد النسخة يجب اعتماد توزيع التشغيل واختبار المرونة، ثم المرور بمشهد `deployGoLive` وفتح حركة المستخدمين صراحة.
- **المرونة اختبار مستقل.** لا تكشف اللعبة نتيجة حالة الخروج قبل تنفيذها. بعد كل اختبار تظهر العلاقة بين الحمل المزاح وما تستطيع المراكز الباقية استقباله، ثم يظهر السقف الكلي بعد الحالات الثلاث.
- **قبول فجوة المرونة خطوة واحدة.** إذا بقيت فجوة بعد الاختبار يمكن تسجيلها مرة واحدة والانتقال، من دون تأكيد مكرر.
- **الفحوص المؤجلة دين تشغيل حقيقي.** إذا نُقلت للمراقبة تظهر نافذة تكون فيها الخدمة عاملة والفحص ما زال مفتوحًا، ثم يُنفذ ويُغلق.
- **الإصلاح منفصل عن التحقق.** هذا مطبق في فحص قطاع التعدين، صيانة المصنع، تبريد مركز البيانات، استعادة التدريب، ومعالجة سعة الإصدار.
- **إعادة التشغيل استعادة مؤقتة.** إذا بقي الإصدار المشتبه به بعد عودة الخدمة، يجب إما الرجوع عنه أو تسجيل دين تشغيلي مفتوح تحت المراقبة قبل الانتقال إلى الدعم.
- **السلامة في هذا السيناريو طبقة سياسة استجابة.** إصلاحها لا يغير أوزان النموذج، لكنه يحتاج إعادة اختبار وبوابة انحدار.
- **التقدم لا يساوي دخول المرحلة.** شريط الرحلة يتقدم داخل كل مرحلة ولا يصل إلى 100% إلا عند `abstract8`.

## التشغيل محليًا

المشروع HTML/CSS/JavaScript باستخدام ES modules أصلية. لا توجد خطوة build، ولا backend، ولا قاعدة بيانات، ولا حساب مستخدم.

```bash
python3 -m http.server 4173
```

ثم افتح `http://127.0.0.1:4173/`.

## الحفظ والخصوصية

التقدم وإعدادات الوصول تحفظ في `localStorage` فقط. لا يرسل الطلب التجريبي إلى خادم خارجي. مخطط الحالة الحالي هو **schema v8**.

لا يحتوي runtime الحالي على migrations أو حقول توافق لإصدارات اللعبة السابقة. إذا وجد المتصفح حفظًا من schema أقدم أو حالة لا تطابق البنية الحالية، تبدأ اللعبة جلسة جديدة مع تنبيه واضح بدل تشغيل كود تاريخي داخل النسخة الحالية. هذا قرار تنظيف متعمد لإبقاء مصدر الحقيقة واحدًا بعد حذف أكواد الإصدارات القديمة.

## بنية المشروع

- `index.html`: صفحة التشغيل الوحيدة؛ لا توجد صفحات تشغيل قديمة موازية.
- `js/app.js`: ربط المكونات والمسارات والحالة، مع فصل تحذيرات حفظ التقدم عن تحذيرات حفظ الإعدادات.
- `js/scenes/`: منطق المشاهد الحالية فقط.
- `js/domain/game-rules.js`: المصدر المشترك لقواعد الحوسبة والحوكمة والمرونة والاستعادة.
- `js/domain/game-schema.js`: القواميس المركزية لمعرفات الحالات والبوابات والمراحل التشغيلية التي يستخدمها التحقق والتخزين.
- `js/data/`: المحتوى وتعريفات المراحل والشخصيات.
- `js/components/`: مكونات واجهة قابلة لإعادة الاستخدام.
- `js/core/`: التخزين، الحالة، التوجيه، السجل، القرارات والوصول.
- `css/`: نظام العرض الحالي فقط؛ لا توجد طبقات patch تاريخية.
- `tests/`: فحوص static/schema/CSS ومتصفح وregression، ومنها حارس يفرض وجود صفحة HTML واحدة ويمنع رجوع حقول ومهاجرات الإصدارات القديمة ويكشف الحالة التشغيلية التي تُكتب بلا قراءة، ويتحقق من أن كل ملف JavaScript تشغيلي قابل للوصول فعليًا من `js/app.js` لا مجرد مستورد من ملف معزول آخر.
- `docs/`: التصميم والمنهجية والسرد والمعمارية وسجل المراجعات.

```bash
npm ci --ignore-scripts
npm run audit:ci
npm run check:syntax
npm run check:lint
npm run check:static
npm run check:storage
npm run check:css
npm run test:browser
npm run test:journey
npm run test:regression:data-governance
npm run test:regression:revisions-failover
npm run test:regression:guidance-history
npm run test:regression:causality-results
npm run test:regression:state-roles
npm run test:regression:clarity-remediation
```

الـCI يفحص البنية والمخطط وCSS، ثم الرحلة الكاملة والرحلات السببية والاختبارات المتخصصة على المتصفح مع اختبارات الوصول والمحركات الإضافية.
