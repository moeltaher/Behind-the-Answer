# Fourth Audit Verification

توثق هذه الجولة المشكلات التي بقيت بعد الجولة الثالثة وكيف أُغلقت في منطق اللعبة واختباراتها.

## 1. إعادة التدريب لا تعيد استخدام أدلة نسخة قديمة

- الحالة تستخدم `candidateRevision`.
- `dataCurrentTrainingUsed` يصف بيانات النسخة الحالية.
- `dataTrainingUsed` يحتفظ بتاريخ كل مادة دخلت أي جولة معالجة.
- إذا تعذر حسم مادة مستخدمة بدليل واضطر اللاعب إلى استبعادها، تنشأ revision جديدة وتُعاد جولة post-training.
- `resetCandidateEvidence` يبطل معايرة التقييم، تقييم checkpoint، السلامة، بوابات الإصدار، الإطلاق والتشغيل المرتبط بالنسخة السابقة.
- تاريخ المادة المستبعدة لا يمحى.

## 2. N-1 أصبح حساسًا لتوزيع الحمل

السعات 60/45/35 والحمل الكلي 100 تجعل مجموع headroom ثابتًا. لذلك لا تستخدم اللعبة مجموع الهامش ولا مجرد جمع السعة الباقية كمقياس يميز التوزيعات.

يعلن السيناريو قيدًا إضافيًا: كل موقع باقٍ يستطيع استقبال بحد أقصى 20 نقطة حمل إضافية لحظيًا عبر failover. لكل موقع باقٍ تحسب القدرة القابلة للاستقبال:

`min(هامش السعة، 20)`

ثم تقارن مجموعها بالحمل المزاح.

الاختبارات تثبت أن:

- توزيع `45/30/25` يتحمل 1 من 3 حالات خروج كاملة.
- توزيع `60/5/35` يتحمل 0 من 3.

وبذلك أصبح اختيار اللاعب مؤثرًا في النتيجة.

## 3. بوابة حوكمة البيانات لا تستطيع إعلان نجاح زائف

إذا كانت revision الحالية تحتوي مادة ذات `unresolved`:

- تظهر بوابة السلامة/الخصوصية/حوكمة البيانات مقفلة.
- لا يظهر زر اعتمادها.
- لا يمكن حفظ `risk` داخل `releaseGates` في حالة تحمل حاجبًا حاليًا.

## 4. لا توجد جولة post-training بلا مدخلات

زر بدء الجولة لا يتاح إلا إذا:

- أغلقت قرارات أهلية كل مادة غير محسومة؛ و
- وجد مدخل واحد على الأقل: مادة بيانات مؤهلة أو مثال تصنيف بشري مؤكد.

## 5. العمل المؤجل للمراقبة يظل عملًا حقيقيًا

- `extraChecks`: فحوص أُنجزت قبل الإطلاق.
- `deferredExtraChecks`: فحوص كانت لا تزال معلقة ونقلت صراحة إلى المراقبة.
- `monitoringChecksCompleted`: فحوص نُفذت وأغلقت بعد الإطلاق.

إذا اكتملت كل الفحوص قبل الإطلاق لا يظهر خيار «أطلق وانقل المتبقي» لأنه لم يعد هناك متبقٍ. وإذا نُقل فحص إلى المراقبة، يظهر بعد الإطلاق مع إجراء ودليل ونتيجة قبل متابعة توزيع الحمل.

## 6. إدارة التركيز بعد إعادة رسم المشهد

`router.html()` يتحقق مما إذا كان التركيز داخل المشهد قبل استبدال HTML. بعد إعادة الرسم ينتقل إلى:

1. feedback ظاهر يحمل `role="status"`، أو
2. عنوان `<h1>`.

يغطي الاختبار حالة التحقيق في بوابة السعة التي تعيد رسم `launchDecision` من دون تغيير route.

## 7. شاشة النتائج تعرض lineage البيانات

تعرض النهاية كل مادة بحسب إحدى الحالات:

- ضمن revision الحالية.
- استُخدمت تاريخيًا ثم خرجت من النسخة الحالية.
- موقوفة قبل post-training.
- معلقة في workflow ولم تدخل التدريب.
- مستبعدة قبل التدريب.

بهذا لا يختفي تاريخ المعالجة عند عرض الحالة الحالية.

## 8. المشهد نفسه جزء من صحة الحالة

schema v4 لا تقبل اسم route صحيحًا وحده. أمثلة العلاقات المفروضة:

- `trainingRun` يحتاج revision ومدخلات فعلية.
- `checkpointEval` يحتاج إكمال مهام التقييم ومعايرة المقيّم.
- `launchOutcome` يحتاج قرار إطلاق.
- `deployIncident` يحتاج توزيعًا واختبارات failover الثلاثة.
- الخاتمة تحتاج إغلاق الاستعادة والدعم.
- `finalAnswer/results/finalMessage` تحتاج اجتياز تحدي انتقال التعلم.

الحالات المستحيلة يعاد ضبطها بدل عرض صفحة متقدمة بحالة ناقصة.

## 9. معايرة المقيّم ونقل التعلم

- بعد مهام تقييم الإجابات توجد خطوة معايرة صريحة قبل checkpoint.
- إذا أخطأ اللاعب تعرض قواعد الحكم التي يحتاج إلى مراجعتها.
- تحدي RAG يعرض تفسيرًا لكل عنصر خاطئ وتصنيفه الصحيح بدل الاكتفاء بعدد الأخطاء.

## 10. migration إلى v4

الحفظ من v3 أو v2 أو إصدار أقدم الذي وصل إلى post-training أو ما بعده يعود إلى `trainingSetup`.

السبب أن تلك الإصدارات لا تحفظ المعلومات التي تسمح بإثبات:

- أي مواد موجودة في النسخة الحالية مقابل الاستخدام التاريخي؛
- هوية revision المرشحة؛
- أن أدلة التقييم والسلامة والإصدار تخص تلك revision؛
- دين المراقبة بعد الإطلاق.

## الاختبارات

CI يشغل:

```text
npm run audit:ci
npm run check:syntax
npm run check:lint
npm run check:static
npm run check:storage
npm run check:css
npm run test:browser
npm run test:fourth-audit
```

`tests/fourth-audit.mjs` يركز على مشكلات هذه الجولة، بينما `tests/smoke.mjs` يغطي الرحلة الكاملة والموبايل والهجرة والوصول وإدارة التركيز والمتصفحات المختلفة.
