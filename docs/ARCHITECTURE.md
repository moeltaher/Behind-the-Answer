# بنية اللعبة الحالية

هذه الوثيقة تصف البنية الحالية فقط. تاريخ الجولات موجود في `AUDIT-HISTORY.md`.

## التطبيق

اللعبة تطبيق ثابت من HTML وCSS وJavaScript باستخدام ES modules، من دون backend أو قاعدة بيانات أو حساب مستخدم. `index.html` هي صفحة التشغيل الوحيدة، والحالة والإعدادات تحفظ في `localStorage`.

الحالة الحالية تستخدم `schemaVersion: 8`. لا يحتفظ runtime الحالي بمسارات migration أو حقول توافق لإصدارات اللعبة السابقة. إذا وجد التخزين حفظًا من schema أقدم أو حالة لا تطابق البنية الحالية، يبدأ التطبيق جلسة جديدة مع تنبيه واضح بدل تشغيل حالة قديمة لا يمكن ضمان اتساقها السببي.

## مصادر الحقيقة

- `js/app.js` — تركيب التطبيق، تسجيل routes، الإعدادات والخلفيات، وفصل تحذيرات حفظ التقدم عن الإعدادات.
- `js/core/state.js` — شكل الحالة الافتراضية الحالية فقط.
- `js/core/storage.js` — التحقق من schema الحالية والعلاقات السببية والحفظ وإعادة الضبط عند عدم التوافق.
- `js/domain/game-rules.js` — المصدر المشترك لقواعد المجال: الحوسبة، مسائل البيانات غير المحسومة، الفحوص الإضافية، سعات التشغيل، المرونة، والتحقق من الاستعادة.
- `js/domain/game-schema.js` — القواميس المركزية لمعرفات الاختيارات والبوابات ومراحل الإصلاح/التحقق التي يشترك فيها state والتخزين والاختبارات.
- `js/data/stage-backgrounds.js` — ربط المشاهد بالمجموعات البصرية وترتيب `SCENE_ORDER`.
- `js/data/stage-tasks.js` — الهدف والقيد وشرط الانتهاء لكل مرحلة.
- `js/components/scene-guidance.js` — العرض المرئي للمهمة والتقدم، مع استهلاك الحالة التشغيلية الحالية بدل استنتاجها من سجل القرارات.
- `js/scenes/` — منطق كل مشهد والأحداث والقرارات والتنقل.

## مجموعات المشاهد

`SCENES_BY_STAGE` يفصل:

- `prelude`: البداية والانتقال من الواجهة.
- المراحل الثماني: mining إلى deployment.
- `ending`: تركيب النظام، الإجابة الأصلية، تحدي نقل التعلم، والنتائج.

في التقييم فُصلت مراجعة حوكمة البيانات عن مراجعة بوابات الإصدار وعن قرار الإصدار. وفي التشغيل أصبح التسلسل: توزيع الحمل → اختبار المرونة → فتح الحركة (`deployGoLive`) → المراقبة عند وجود فحوص مؤجلة → الحادث والاستعادة. هذا يجعل اسم route مطابقًا للمهمة الفعلية ويمنع القفز من الجاهزية إلى خدمة مفتوحة ضمنيًا.

## قواعد الحالة

تخزن الحالة التشغيلية ما يلزم لاستمرار السببية، بينما يحتفظ السجل بالتاريخ فقط. من الأمثلة:

- `miningInspectionMode / miningInspectionStage` لفصل نوع الفحص عن مراحله: `idle / inspect / diagnosed / repaired / verified`.
- `factoryDisposition / factoryProductionStage / factoryRemediationStage` لفصل قرار الإنتاج عن إكمال الدفعة والفحص النهائي والتشخيص والإصلاح والتحقق.
- `dataStatuses` لحالة مسار المادة.
- `dataChecks` لأدلة الحقوق والخصوصية والملاءمة المستقلة.
- `dataTrainingApproved / dataTrainingHeld` لقرار الأهلية.
- `dataCurrentTrainingUsed` للنسخة الحالية و`dataTrainingUsed` للتاريخ.
- `candidateRevision` لربط أدلة التقييم بنسخة مرشحة محددة.
- `dcCoolingStage` لفصل قرار الاستمرارية عن الإصلاح وعن إثبات عودة التبريد.
- `trainingRecoveryStage` لفصل إصلاح الحوسبة عن التحقق من 8/8.
- `releaseCapacityStage` لفصل التشخيص والمعالجة وإعادة القياس.
- `releaseGates / extraChecks / deferredExtraChecks / monitoringChecksCompleted` لتتبع العمل المفتوح والمنجز حول الإصدار.
- `deployDraftLoad / deployLoad / deployFailoverChecks / deployResilienceAccepted` لتتبع محاولة التوزيع واختبارات المرونة وقبول الفجوة.
- `deployTrafficOpen / deployMonitoringOpened` لجعل فتح الخدمة والمراقبة حالتين تشغيليتين واضحتين.
- `deployRecovery / deployRecoveryVerifiedFor / deployRecoveryDisposition` لفصل إجراء الاستعادة عن التحقق وعن مصير الخطر المتبقي.

حقول مثل `trainingCompute` و`tookBreak` و`dcCoolingRestored` و`miningInspectionCount` و`factoryProductionComplete` ليست جزءًا من schema v8 ولا توجد داخل runtime الحالي. كما أزيلت الحالات الوصفية أو الحقول التي لا تؤثر في التشغيل، مثل `dataFollowup.reason` وحالة المهمة `resumed`.

### سجل القرارات ليس state خفيًا

`decisions` سجل append-only لما فعله اللاعب. لا يجوز استخدام وجود decision id كشرط لتحديد الوضع التشغيلي الحالي أو فتح مسار. إذا كانت الشاشة تحتاج معرفة هل تم الإصلاح، التحقق، فتح الحركة، إكمال الدفعة أو قبول فجوة، فيجب أن توجد حالة صريحة داخل `flags`/enum.

هذا الفصل مهم لأن السجل قد يحتوي على قرار يخص محاولة سابقة أو نسخة مرشحة سابقة، بينما الحالة الحالية يجب أن تعكس المحاولة النشطة فقط.

## السببية في المعالجة والاستعادة

- التعدين: قرار الإغلاق → فحص → تشخيص → إصلاح → تحقق. كل مرحلة محفوظة ويمكن استئنافها بعد إعادة التحميل.
- المصنع عند الإيقاف: إيقاف → تشخيص → إصلاح → تحقق → استئناف وإكمال الدفعة → فحص نهائي.
- المصنع عند الاستمرار: قرار الاستمرار → إكمال الدفعة → فحص نهائي → إصلاح دين الصيانة أو نقله صراحة. القرار نفسه لا ينفذ الإنتاج أو الفحص.
- مركز البيانات: النقل أو التوقف لا يعيدان المجموعة الأصلية؛ الإصلاح ثم التحقق خطوتان مستقلتان.
- التدريب: عند التوقف لا تعتبر الحوسبة مستعادة؛ الإصلاح ثم إثبات 8/8 ثم الاستئناف.
- بوابة السعة: التشخيص لا يغير القياس؛ المعالجة لا تغلق البوابة قبل إعادة القياس.
- التشغيل: لا تظهر نتيجة حالة خروج مركز قبل تنفيذ اختبارها. بعد الاختبار تعرض الواجهة الحمل المزاح، الاستقبال الفعلي، والعجز إن وجد. السقف الكلي يظهر بعد الحالات الثلاث.
- فتح الخدمة: اعتماد الإصدار واختبار المرونة لا يساويان go-live؛ `deployTrafficOpen` يجب أن يصبح true بفعل مستقل.
- الحادث: إعادة التشغيل أو rollback لا يثبتان عودة الخدمة؛ `deployRecoveryVerifiedFor` يسجل التحقق، ثم يحسم disposition للخطر المتبقي.

## قواعد المجال المشتركة

`js/domain/game-rules.js` هو المصدر الوحيد للحسابات والقواعد النقية المشتركة، ومنها:

- `MIN_COMPUTE_TO_CONTINUE` و`TRAINING_COMPUTE`.
- `hasUnresolved` ومشتقات حواجز البيانات.
- `neededExtraChecks` و`confirmedAnnotations`.
- `DEPLOY_CAPACITY_LIMITS` و`FAILOVER_INGRESS_LIMITS` و`MAX_SURVIVABLE_FAILURES`.
- `failoverCase` و`survivableFailures` و`hasResilienceResolution`.
- `recoveryDispositionComplete`.

إذا تغيرت قاعدة حسابية، يجب تعديل المصدر المشترك لا إنشاء نسخة داخل `storage.js` أو أحد المشاهد. وإذا كان التغيير في vocabulary أو enum مشترك، يعدل `game-schema.js` بدل تكرار القوائم.

## العرض والوضوح

- `character-card.js` — الشخصية الرئيسية.
- `characters.js` — يربط المشاهد بمن يقود الفعل فعليًا؛ شاشات السلامة يقودها safety tester، الحوكمة rights reviewer، والإصدار release manager.
- `supporting-role-strip.js` — الأدوار الداعمة عند دخولها قرارًا أو تنفيذًا.
- `abstraction.js` — يشرح كيف يختصر النظام العمل؛ لا يقول إن الناتج يتحول حرفيًا إلى المرحلة التالية.
- `progress.js` — تقدم تراكمي داخل المرحلة؛ يبدأ stage 8 دون 100% ويصل إلى 100% عند `abstract8` فقط.
- `task-flow.js` — الحالات الحالية: active / decision / action / debt / complete؛ «قرار مطلوب» للمفاضلات الحقيقية و«تنفيذ مطلوب» للإصلاح أو القياس أو التحقق.
- `scene-guidance.js` — يعرض الدين والحالة التشغيلية الحالية، وعناوين المهمة المختصرة تصف الفعل المطلوب الآن بدل جمع شرح المرحلة كله في العنوان.
- hierarchy العناوين يُنشأ صحيحًا داخل المكونات والمشاهد نفسها؛ لا توجد طبقة post-render تعيد كتابة `h3/h4` بعد العرض.

## الملفات القديمة

لا توجد صفحة تشغيل قديمة إلى جوار `index.html`. الفحص الساكن يفرض وجود ملف HTML واحد فقط. كما تكشف اختبارات static وCSS الملفات والـexports والصور والselectors غير المستخدمة.

لا توجد migrations أو طبقة compatibility تاريخية داخل `storage.js`. الحارس `legacy-cleanup.mjs` يمنع عودة حقول الإصدار السابق، وظائف migration القديمة، أو patch تصحيح العناوين بعد الرندر. تبقى `AUDIT-HISTORY.md` وثيقة تاريخية فقط وليست كود تشغيل أو صفحة runtime.

## الاختبارات

- `static-integrity.mjs`: الاستيرادات والملفات والـexports والأصول والمشاهد، ويشترط `index.html` وحدها، ويفحص write-only gameplay state بعد استبعاد ملفات schema/storage.
- `storage-schema.mjs`: schema v8 والعلاقات السببية والحالات الانتقالية الحالية، ويرفض الحفظ من schema أقدم بدل ترحيله.
- `legacy-cleanup.mjs`: يمنع عودة مسارات migration والحقول والـpatches القديمة إلى runtime.
- `css-integrity.mjs`: selectors وcustom properties وkeyframes.
- `smoke.mjs`: رحلة أساسية متعددة المقاسات، اختبارات إعادة التحميل والسببية، axe، Firefox وWebKit.
- `full-journey.mjs`: الرحلة الكاملة على desktop/mobile ومحركات متعددة مع فحوص وصول.
- مجموعات `regression-*`: حوكمة البيانات، النسخ المرشحة، المرونة، الإرشاد، النتائج، الأدوار، والوضوح والمعالجة.

لا تنشئ وثيقة تحقق مستقلة لكل جولة؛ التاريخ موحد في `AUDIT-HISTORY.md` والاختبارات هي الحارس التنفيذي للبنية الحالية.
